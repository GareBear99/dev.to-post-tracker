# LibHunt and Discovery Lane

LibHunt, SaaSHub, AlternativeTo, and curated awesome lists are not normal social auto-post targets. Treat them as SEO/discovery assets that need clean submissions, monitoring, and occasional updates.

## LibHunt role

LibHunt is useful because it tracks open-source libraries and alternatives. For GitHub repositories, a common discovery check is replacing `github.com` with `libhunt.com` in the repository URL or using LibHunt's project submission page.

Examples:

```text
https://github.com/GareBear99/FreeEQ8
https://libhunt.com/GareBear99/FreeEQ8
```

```text
https://github.com/GareBear99/ARC-Neuron-LLMBuilder
https://libhunt.com/GareBear99/ARC-Neuron-LLMBuilder
```

## Discovery target types

| Type | Examples | Best content |
|---|---|---|
| Alternatives directory | LibHunt, SaaSHub, AlternativeTo | concise project description, repo URL, public page, tags |
| Curated GitHub list | awesome-juce, awesome-vst, awesome-machine-learning, awesome-local-ai | one-line PR entry with repo link and honest scope |
| Editorial/review | music tech blogs, open-source newsletters | short pitch, screenshots, changelog, demo link |
| Community | Reddit, Mastodon, Discord | human-written intro plus DEV.to article link |

## Standard discovery description templates

### FreeEQ8

```text
FreeEQ8 is a free, open-source JUCE/C++ 8-band parametric EQ plugin for VST3/AU workflows, focused on advanced EQ features such as dynamic EQ, match EQ, M/S processing, oversampling, analyzer views, and linear-phase mode.
```

### ARC-Neuron LLMBuilder

```text
ARC-Neuron LLMBuilder is a local-first LLM lifecycle framework for governed model improvement, benchmark receipts, candidate/incumbent promotion, archive-ready lineage, and reproducible small-model experimentation.
```

### AI Desk Meter

```text
AI Desk Meter is an open-source, local-first runtime dashboard foundation for MuseMeter, designed to show AI/muse status, local runtime signals, provider state, and companion-device friendly status output.
```

## Discovery workflow

1. Publish or update the DEV.to article.
2. Confirm the repo README has matching title, description, topics, public page, and screenshots if possible.
3. Submit/refresh the directory listing.
4. Record status in a manual tracking table.
5. Add the listing URL back into the repo README or public IO page when accepted.
6. Use DEV.to follow-up posts for real updates, not spammy repeated submissions.
